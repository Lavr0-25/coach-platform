## Зачем

152-ФЗ, ст. 18 ч. 5: при сборе персональных данных (в т.ч. через интернет)
оператор обязан обеспечивать запись, хранение и уточнение ПДн граждан РФ
**на территории РФ**. Сейчас платформа живёт в Supabase (за пределами РФ) и
на Vercel — соответствия нет на двух уровнях сразу: БД и хостинг.

## Размеры (замер 2026-09-03)

- База целиком: **15 МБ** (самая большая таблица — analytics_events, 264 КБ).
- Storage: **21 МБ** (32 файла: обложки, файлы уроков, скриншоты).

### Прогноз на 10 000 активных пользователей

~0,5–2 МБ данных на пользователя в год (аналитика, прогресс, сообщения,
комментарии, уведомления):

| Горизонт | База | Storage |
|---|---|---|
| 10 000 юзеров, 1 год | 5–20 ГБ | 50–100 ГБ |
| 10 000 юзеров, 3 года | 20–60 ГБ | 100–300 ГБ |

Для Postgres это малая база. Видео хранится на YouTube/VK (embed) и в базу
не попадает; главный фактор роста — файлы Storage. Загрузка собственных
видео — отдельное решение, в план переноса не входит.

## Варианты размещения — два приоритетных (согласовано 2026-09-03)

Отклонённые альтернативы: гибрид «ПДн отдельно от контента» (две БД, развязка
auth — сложность не окупается) и управляемая БД в РФ-облаке (в 2–3 раза
дороже при наших объёмах; запасной вариант, не приоритет).

### Вариант 1: свой сервер на базе ноутбука Анатолия (приоритет с 18.09 вечера)

- **Решение Анатолия 18.09:** до первых поступлений и реальных авторов
  постоянные расходы (~1 800 ₽/мес на VPS) на продукт не запускаем.
  VPS Timeweb остаётся планом на период, когда оборот окупит его.

- Постановка: ноутбук 24/7, Ubuntu Server + Docker (Postgres + приложение),
  автобэкап, автостарт контейнеров после ребута.
- Доступ из интернета: статический IP у провайдера или Cloudflare Tunnel
  (второй безопаснее — без открытых портов).
- ⚠️ Батарея: вечная зарядка → риск вздутия. Вынуть батарею (если съёмная)
  или лимит заряда 60–80% в фирменной утилите. Плюс сетевой фильтр.
- Цена: ~0 ₽ (+ возможно 150–300 ₽/мес за статический IP).
- Риск: отключение света/интернета = недоступность до восстановления.
- **18.09: приоритет вернулся на ноутбук** (отказ от постоянных расходов
  до поступлений); Анатолий проверит параметры железа — ждём CPU/RAM/диск.
  VPS — вариант 2 ниже, сохраняем как план на выручку; стек общий.

### Вариант 2: VPS + Docker (отложен до первых поступлений)

- **Требование по RAM выросло**: официальный минимум Supabase self-hosted —
  4 ГБ, но стек (12–15 контейнеров) в простое ест 3–4 ГБ; production-гайды
  2026 сходятся на 8 ГБ (на 4 ГБ — риск OOM-killer, exit 137). База мала
  (15 МБ) — RAM нужен под сам стек. Итог: **4 vCPU / 8 ГБ**, не 2/4.
- **Выбор (18.09, рекомендация агента): Timeweb Cloud, Cloud MSK 80**
  (4×3.3 ГГц, 8 ГБ, 80 ГБ NVMe, Москва) — ~1 782 ₽ + ~180 IPv4 ≈
  **~1 960 ₽/мес**. Почему он:
  - SMTP-порты 25/465/587 разблокируются **из панели** (у всех РФ-провайдеров
    они закрыты по умолчанию; у Selectel на VDS не разблокируют вообще, у
    Beget IP в спам-листах) — а email-верификация (№16) сливается с №9;
  - почасовая оплата — стенд можно поднять на день-два (~60 ₽) для
    эксперимента и погасить;
  - готовый образ Docker при создании, API/CLI/Terraform, SLA 99.98%;
  - бэкапы: снапшоты 6 ₽/ГБ (свой pg_dump по cron — основной слой).
- Альтернативы: reg.ru Std C8-M8-D120 (3 520 ₽ — в 1.8× дороже, резерв:
  у Анатолия уже аккаунт и домены), Selectel (дешевле, но SMTP-блокировка
  без разблокировки на VDS → отпадает), Beget (посуточная тарификация и
  бесплатные бэкапы, но IP в спам-листах и SMTP только через их 2525).

### Ключевое архитектурное решение (общее для обоих)

- **Docker-стек, переносимый между вариантами 1 и 2**: любой вариант
  превращается в другой за ~1 час. Можно стартовать на ноутбуке и переехать
  на VPS (или обратно) без переделки.

## Политика паролей (2026-09-12, решение Анатолия)

- **Минимум 8 символов** + блок популярных слабых паролей (ru/en), без
  требования спецзнаков/цифр — по NIST длина важнее наборов, меньше
  требований = меньше брошенных регистраций.
- **Единый модуль `lib/password.ts`** (`validatePassword`, `MIN_PASSWORD_LENGTH`):
  подключён ко всем формам с паролем — регистрация `app/(auth)/register`,
  сброс `app/(auth)/reset-password`, смена пароля в кабинете ментора. Раньше
  правила жили копиями с разными числами (6 и 8).
- **Серверная часть — Supabase Auth**: Minimum password length = 8
  (Authentication → Providers → Email; установлено 12.09). Проверено пробой
  через API: 6 символов → 422 weak_password; 8+ проходит валидацию пароля.
- Слабый список проверяется только на клиенте — это UX-защита; серверную
  гарантию даёт минимальная длина Supabase.
- **Грабля доменов:** анонимная регистрация с @test.ru отклоняется Supabase
  («email invalid» — домен в списке одноразовых). Существующие тестовые
  аккаунты созданы через admin API (проверку пропускает). Новых тестовых
  юзеров создавать только через admin API или с реального домена.
- **Auth**: свой (NextAuth на своей БД) вместо Supabase Auth — иначе
  `auth.users` останется за пределами РФ.
- **RLS сохраняется**: это фича Postgres, переезжает вместе с базой.
- Мой доступ: SSH-ключ (один раз, от Анатолия) → все операции с БД агент
  выполняет сам через терминал; участие Анатолия — «ОК» на критичные
  действия. Ключи/пароли — только локально, не в репозитории.

## Security-заголовки (реализовано 2026-09-18)

Задаются централизованно в `next.config.ts` (`headers()`) — применяются ко всем
путям, и в dev, и на проде. Vercel добавляет HSTS сам (2 года, preload).

| Заголовок | Значение | От чего защищает |
|---|---|---|
| Content-Security-Policy | `default-src 'self'`; скрипты — только свои + инлайн (Next-бутстрап); стили — свои + инлайн (Tailwind/Tiptap); `connect-src` — Supabase (https+wss); `frame-src` — плееры уроков (YouTube/VK/Rutube/Дзен — `lib/video-embed.ts`); `img-src` — https (WYSIWYG-контент может ссылаться на любой хост); `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `frame-ancestors 'self'` | Встраивание чужих скриптов (вектор XSS через внешний CDN), нежелательные встраивания |
| X-Frame-Options | SAMEORIGIN | Кликджекинг (дубль frame-ancestors для старых браузеров) |
| X-Content-Type-Options | nosniff | MIME-sniffing (браузер не «угадывает» тип файла) |
| Referrer-Policy | strict-origin-when-cross-origin | Утечка адресов страниц (в т.ч. приватных URL кабинета) во внешние сервисы |
| Permissions-Policy | camera/microphone/geolocation/display-capture запрещены | Браузерные API, продукту не нужные |

Компромиссы v1 (осознанные):
- `script-src` с `'unsafe-inline'` — Next вставляет инлайн-бутстрап-скрипты
  без nonce. Главный вектор (внешние скрипты) закрыт; строгий CSP с nonce
  через middleware — отдельная задача при росте требований.
- `img-src https:` — контент уроков (WYSIWYG) может содержать картинки
  с любых https-хостов, не ломаем пользовательский контент.
- В dev к script-src добавляется `'unsafe-eval'` (React Refresh) и к
  connect-src `ws://localhost:*` (HMR) — только локально.

Проверено (18.09): заголовки на dev-сервере; regression-прогон (главная,
логин, кабинет, редактор Tiptap, публичный урок, аналитика) — 0 ошибок
консоли, CSP-нарушений нет; production-сборка чистая.

## Юридический минимум (не зависит от выбора хостинга)

- Уведомление Роскомнадзора об обработке ПДн (оператор).
- Политика конфиденциальности на сайте + фиксация согласий
  (`user_consents` — таблица уже есть).
- Минимизация: не собирать данные, не нужные продукту (например, IP —
  только для доказательства согласия и модерации).

## План переноса (когда решим стартовать)

1. RLS-аудит и исправление политик (идёт параллельно, см. docs/backlog.md).
2. Подготовка Docker-стека: Postgres + Next.js + бэкап по cron.
3. Выбор варианта (ноутбук / VPS), поднятие стенда, SSH-доступ агенту.
4. Auth: NextAuth на своей БД, перенос аккаунтов (сброс паролей
   пользователей или перенос хэшей).
5. Дамп данных из Supabase → восстановление на своём Postgres.
6. Storage: выгрузка файлов из бакетов → локальное хранилище/MinIO.
7. Переключение DNS с Vercel на свой сервер, наблюдение 1–2 недели.
8. Supabase-проект не удаляем до полной уверенности (откат = переключение DNS).

### Два пути (оценка 2026-09-15)

**Путь А — self-hosted Supabase в Docker (выбран для проработки):**
Supabase открыт — поднимается у себя тем же стеком (Auth/Storage/API/RLS/pg_cron).
Код почти не трогается: меняются URL и ключи в env, клиентские вызовы остаются.

- Объём: **~5–7 сеансов** (Docker-стек 2–3, дамп БД+Storage 1–2, SMTP+верификация 1,
  DNS-переключение 0,5) + 1–2 недели наблюдения.
- Минусы: ~5–7 контейнеров, нужно 4 ГБ RAM (ноутбук-вариант уже впритык — фактически
  это решение в пользу VPS), обновления Supabase обслуживаем сами.

**Путь Б — NextAuth + MinIO (ранее зафиксированное решение, теперь запасное):**

- Плюсы: меньше контейнеров, полный контроль.
- Минусы: переписываем Auth (задевает агентские magic-link-сессии — всё агентское API)
  и слой Storage. **+5–7 сеансов** сверху (итого ~10–14).

## MCP и доступ агента (2026-09-18)

- Self-hosted Supabase отдаёт **MCP-эндпоинт `/mcp` через API-gateway**
  (Kong/Envoy) — те же инструменты, что сейчас в облаке (execute_sql,
  миграции, таблицы). Официальная документация: подключать **только через
  SSH-туннель** (эндпоинт не для интернета), режим `read_only` по умолчанию,
  ограничение набора инструментов (`features=database,docs`).
- Запасной вариант: community-MCP с прямым подключением к Postgres
  (сервисный ключ) — работает с любой БД.
- Общий принцип не меняется: SSH-ключ агенту (один раз, от Анатолия),
  участие Анатолия — «ОК» на критичные действия.

## SMTP и почта (2026-09-18, сливается с №16)

- Прямая отправка с РФ VPS через порт 25 не работает ни у кого (антиспам).
- План: SMTP-релей (Timeweb smtp.timeweb.ru или сторонний) + свой домен
  + **SPF, DKIM, DMARC** + PTR — обязательные DNS-записи доставляемости.
- На этом же шаге включается email-верификация при регистрации (№16).
